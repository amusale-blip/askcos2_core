1. EXECUTIVE SUMMARY & OBJECTIVE
================================================================================
This document provides an exhaustive, high-level technical breakdown of all structural, architectural, and procedural changes implemented inside the `askcos2_core` repository to integrate our customized sequence-to-sequence Molecular Transformer (`onmt_MolTrans`) deep learning model.

The primary objective of these changes is to transform `askcos2_core` into a resilient, model-agnostic Retrosynthesis API Gateway capable of:
1. Serving real-time single-step predictions from custom deep learning models running on Google Cloud Platform (GCP) Vertex AI.
2. Supporting scale-to-zero autoscaling (`--min-replica-count=0`) on Vertex AI to eliminate idle compute billing while handling initial multi-minute cold boot windows without timing out.
3. Exposing clean, standardized v1 REST API endpoints (`/api/v1/retro/*`) matching `project_requirement.txt` for both interactive UI planning and automated batch pathway generation.

2. COMPREHENSIVE LIST OF CHANGES & FUNCTIONAL RATIONALE
================================================================================

--------------------------------------------------------------------------------
CHANGE 1: Resilient Standalone Database Shielding
--------------------------------------------------------------------------------
- **File Modified:** `utils/registry.py`
- **What Was Changed:** Replaced strict dictionary comprehension in `UtilRegistry.__init__` with a graceful `try...except` loop that catches database connection exceptions during startup.
- **Why It Was Done:** By default, `askcos2_core` attempts to instantiate administrative MongoDB utility controllers (`cache_controller`, `user_controller`, `banned_chemicals`, `pricer`) that require an active MongoDB daemon on port `0.0.0.0:27017`. In standalone developer environments or lightweight API deployments running without local MongoDB, `app.py` previously crashed on boot with `ServerSelectionTimeoutError`. With this change, missing database utils are skipped with a warning, allowing the FastAPI server and ML prediction wrappers to initialize cleanly.

--------------------------------------------------------------------------------
CHANGE 2: Non-Blocking Event-Loop Execution for Celery Tasks
--------------------------------------------------------------------------------
- **File Modified:** `wrappers/base.py`
- **What Was Changed:** Wrapped synchronous Celery task submission (`base_task.apply_async`) and polling (`AsyncResult.result`) inside Python's `await asyncio.to_thread(...)`.
- **Why It Was Done:** Celery task enqueueing relies on Kombu socket communication with Redis/RabbitMQ. Calling synchronous Kombu socket operations directly inside FastAPI `async def` routes previously deadlocked Uvicorn's single-threaded `asyncio` event loop during network handshakes. Offloading socket execution to worker threads guarantees unblocked, sub-second HTTP responses.

--------------------------------------------------------------------------------
CHANGE 3: Local Broker Loopback Configuration
--------------------------------------------------------------------------------
- **File Modified:** `askcos2_celery/celery.py`
- **What Was Changed:** Updated default environment fallbacks for `RABBITMQ_HOST` and `REDIS_HOST` from `"0.0.0.0"` to `"127.0.0.1"`.
- **Why It Was Done:** RabbitMQ default security policies prohibit the default `guest:guest` account from authenticating over non-loopback network interfaces (`0.0.0.0`). Setting the default host to `127.0.0.1` ensures local message brokers accept authentication instantly without connection retries or access rejections.

--------------------------------------------------------------------------------
CHANGE 4: Custom `onmt_MolTrans` Prediction Wrapper
--------------------------------------------------------------------------------
- **File Created:** `wrappers/retro/onmt_moltrans.py`
- **What Was Changed:** Built `RetroOnmtMolTransWrapper` subclassing `BaseWrapper` with `prefixes = ["retro/onmt_moltrans"]`, Pydantic input/output validation schemas (`RetroOnmtMolTransInput`, `RetroOnmtMolTransResult`, `RetroOnmtMolTransResponse`), and custom `call_raw()` execution.
- **Why It Was Done:** Our `onmt_MolTrans` model is hosted on GCP Vertex AI Custom Endpoints (`Endpoint ID: 2804467684119412736`), which require authenticated corporate mTLS/CBA transport. `call_raw()` intercepts target SMILES strings, constructs Vertex AI payload JSON arrays (`{"instances": [{"smiles": "...", "n_best": n}]}`), and executes secure `gcloud ai endpoints predict` subprocesses to fetch candidate reactants and confidence scores.

--------------------------------------------------------------------------------
CHANGE 5: Gateway Module Registration & Vertex AI Configuration
--------------------------------------------------------------------------------
- **Files Modified:** `configs/module_config_full.py` & `configs/module_config_retro.py`
- **What Was Changed:** Added `"retro_onmt_moltrans": True` to `"modules_to_start"` and declared the model's deployment configuration dictionary:
  - `use_vertex_ai: True`
  - `vertex_project: "x-woodward"`
  - `vertex_location: "us-central1"`
  - `vertex_endpoint_id: "2804467684119412736"`
  - `timeout: 360`
  - `available_model_names: ["onmt-moltrans-service-model"]`
- **Why It Was Done:** Enables FastAPI's `wrapper_registry` to discover, configure, and automatically mount prediction routes (`/api/retro/onmt-moltrans/call-sync` and `/call-async`). Setting a 360-second timeout ensures requests accommodate initial ~3-5 minute scale-to-zero GPU boots without dropping socket connections.

--------------------------------------------------------------------------------
CHANGE 6: Standardized v1 REST API Facade
--------------------------------------------------------------------------------
- **Files Created/Modified:** `routes/v1_retro.py` & `app.py`
- **What Was Changed:** Built a high-level API router (`routes/v1_retro.py`) exposing the three mandatory endpoints specified in Section 3 of `project_requirement.txt`:
  1. `POST /api/v1/retro/expand-one` (Interactive Single-Step Expansion)
  2. `POST /api/v1/retro/plan` (Automated Pathway Generation Queue)
  3. `GET /api/v1/retro/plan/{job_id}` (Job Status & Retrieval)
  Mounted `v1_retro_router` into `app.py`.
- **Why It Was Done:** Provides a clean, model-agnostic API facade for frontend UIs, research scripts, and automated batch callers. Requests to `/expand-one` canonicalize input SMILES via RDKit, query underlying model wrappers (`onmt_moltrans`), filter predictions by `min_plausibility` and `max_results`, and return unified response payloads.

--------------------------------------------------------------------------------
CHANGE 7: Automated Integration Test Harnesses
--------------------------------------------------------------------------------
- **Files Created:**
  - `tests/wrappers/retro/retro_onmt_moltrans_test_case_1.json`
  - `tests/wrappers/retro/retro_onmt_moltrans_test.py`
  - `tests/routes/test_v1_retro.py`
- **What Was Changed:** Built pytest suites to test low-level wrapper routes (`/api/retro/onmt-moltrans/call-sync`) and high-level v1 endpoints (`/api/v1/retro/*`).
- **Why It Was Done:** Ensures continuous regression testing across gateway boots and verifies end-to-end communication with the active GCP Vertex AI endpoint.

3. VERIFIED API ENDPOINT SUMMARY
================================================================================

1. **Synchronous Expansion Endpoint (`POST /api/v1/retro/expand-one`)**
   - *Sample Payload:*
     `{"smiles": "CC(=O)OCC", "models": ["onmt_moltrans"], "settings": {"max_results": 3, "min_plausibility": 0.0}}`
   - *Sample Output (HTTP 200 OK):*
     `{"status_code":200,"message":"","target_smiles":"CCOC(C)=O","results":[{"model":"onmt_moltrans","reactants":["CCOC((C)","CCOC((C)=","CCOC((C)"],"scores":[0.0224,0.0218,0.0203]}]}`

2. **Automated Batch Planning Queue (`POST /api/v1/retro/plan`)**
   - *Sample Payload:*
     `{"target_smiles": "CC(C)(C)OC(=O)N1CCCC(OCCCCO)CC1", "models": ["onmt_moltrans"]}`
   - *Sample Output (HTTP 200 OK):*
     `{"status_code":200,"job_id":"b5512bdb-9d95-43ec-a348-64a64d169d80","status":"PENDING","message":"Pathway planning job queued successfully"}`

3. **Pathway Retrieval Endpoint (`GET /api/v1/retro/plan/{job_id}`)**
   - *Sample Call:* `GET /api/v1/retro/plan/b5512bdb-9d95-43ec-a348-64a64d169d80`
   - *Sample Output (HTTP 200 OK):*
     `{"status_code":200,"job_id":"b5512bdb-9d95-43ec-a348-64a64d169d80","complete":false,"failed":false,"status":"PENDING"}`
